# 프론트엔드 최종 연동 전달서

2026-10-02 / bank-backend v5 최종 기능 누적본. 이 문서를 먼저 읽고 각 업무의 상세 API 문서를 참조한다. 이번 산출물은 백엔드 구현과 연동 계약이며 실제 프론트 화면은 포함하지 않는다.

## 확정 범위

자동이체·공과금·외환·펀드·대출은 이번 범위에서 제외한다. 출력 전용 기능·공지/FAQ·알림·모의 타행·다계좌 이체·QR 인증도 이번 최종본에 구현하지 않았다. 기존 문서의 ‘예정’ 표시는 이 합의로 대체한다. 실제 DB 인프라 통합은 마지막에 별도로 진행한다.

## 문서 적용 순서

공통 최신 범위는 본 문서와 PROJECT_SCOPE.md다. 신원/복구는 5차, PIN/한도·계좌 설정은 4차, 이체는 3차+4차, 예적금은 6차 문서가 우선한다. 2차 문서의 ‘복구 미지원’, 이전 문서의 ‘다음 단계’ 등은 당시 기록이다. 현재 구현은 목록 정렬/숨김, profile assurance, 전체 세션 폐기 등 후속 변경을 포함한다. 단계별 FRONTEND_HANDOFF 문서는 상세 화면 동작을 보충한다.

## 기존 API에서 바뀌는 연결

| 기존 | 신규 화면에서 사용할 API | 차이 |
|---|---|---|
| POST /api/auth/register | POST /api/v2/auth/register | 약관·선택 연락처 grant·멱등 키 |
| POST /api/auth/login | POST /api/v2/auth/login | 같은 인증 체계 |
| GET /api/accounts | GET /api/v2/accounts | items, UUID, 상태·설정·문자열 금액 |
| POST /api/accounts | POST /api/v2/accounts | Idempotency-Key, UUID 반환 |
| GET /api/accounts/{number}/balance | GET /api/v2/accounts/{id} | 번호 대신 UUID |
| GET /api/accounts/{number}/transactions | GET /api/v2/accounts/{id}/transactions | 필터·커서 페이지 |
| POST /api/transfers | v2 receiver-validation/previews/auth/step-up/transfers | PIN·미리보기·단계 승인 |
| POST /api/deposits | 기존 경로 유지, 개발 시연 전용 UI | 모의 현금 생성; CHECKING만 허용 |

기존 API는 호환용으로 남아 있다. 특히 구 가입은 필수 약관을 강제하지 않으므로 신규 화면에서 사용하지 않는다. 구 API 폐기/차단 시점은 프론트 전환과 협의한다. 예적금 계좌에 일반 이체/모의 입금은 409로 거절한다. 예적금 원장도 계좌 거래내역에서 조회하며 v2 일반 transfers 목록에는 포함되지 않는다.

## 화면 흐름

1. 가입: terms 조회 → 체크박스 동의 → 선택적 모의 연락처 확인 → v2 가입 → 로그인 → 복구 코드 발급/보관 안내. 체크 UI는 프론트, 필수 버전 검증과 동의 기록은 서버 책임이다.
2. 연락처: REGISTER 또는 PROFILE challenge → 개발 수신함 → verify → grant 적용. SIMULATED는 실제 인증/실명확인이 아니다. 기본 서버는 발송 비활성이므로 연락처 없이도 가입을 진행할 수 있어야 한다.
3. 계좌: 목록 → 상세/내역. 숨김 계좌는 관리 화면에서 includeHidden=true. 출금 선택에는 ACTIVE/CHECKING/출금 등록 계좌만 표시하고 잔액·한도·PIN 상태를 안내한다.
4. 이체: 수취 확인 → preview → auth/step-up(TRANSFER, PIN이 있으면 함께) → Idempotency-Key로 확정 → 결과. 수취 이름은 검증되지 않은 마스킹 프로필이다. 이름을 실제 은행 실명으로 표시하지 않는다.
5. PIN/출금 등록/한도: 변경할 내용과 version을 묶어 step-up → 동일 changes와 actionToken으로 설정 반영. 분실 PIN은 복구 코드 경로를 사용한다.
6. 예적금: 상품/조건 조회 → 동의 → 출금 계좌·금액 → 비밀번호/PIN → 가입. 적금 상세에서 현재 회차 정액 수동 납입. 해지는 반환 계좌 선택 → 서버 견적 표시 → 비밀번호 → 확정. 전용 step-up 토큰은 쓰지 않는다.
7. 암호 변경/복구/PIN 재설정: 성공하면 로그인 상태·승인 상태·복구 코드 상태를 지우고 재로그인한다. 남은 복구 코드도 폐기되므로 새 코드 발급을 안내한다.

## 프론트 공통 규칙

- Authorization: Bearer <token>. 토큰/PIN/비밀번호/복구 코드/인증번호는 URL·로그·분석 이벤트·영구 브라우저 저장소에 넣지 않는다. TLS, 토큰 보관 방식, XSS 대응은 배포 구성과 함께 확정한다.
- UUID(accountId/customerId/subscriptionId/previewId)는 서로 다른 식별자다. 계좌번호는 문자열로 표시한다.
- v2 금액은 문자열이며 Number/float로 계산하지 않는다. 금액 입력은 서버 허용 소수 자리/범위를 지킨다. 금리 0.03은 3%다.
- 요청 재시도는 최초 Idempotency-Key와 동일 본문. 새 사용자 의도에만 새 키. 버튼 중복 클릭을 막되 서버 멱등성도 함께 사용한다. 새 예적금 가입을 의도적으로 새 키로 요청하면 별도 계약이 생성된다.
- version 충돌 시 GET 재조회 후 사용자 재확인. 설정/납입/견적에 오래된 version을 강제로 재사용하지 않는다.
- 401 REAUTHENTICATION_FAILED는 재입력, UNAUTHORIZED는 재로그인. 기타 기존 API의 401은 상세 계약에 맞게 처리한다. 403 PIN, 409 상태/잔액/충돌, 423 잠금, 429 제한을 구분한다.
- 커서는 서버 반환값을 그대로 전달한다. 필터가 바뀌면 처음부터 조회한다. 조회 날짜는 한국 날짜다.
- 예적금 계좌는 전체 목록에서 accountType으로 구분하고 출금 등록/PIN 메뉴를 숨긴다. 별명·숨김·내역 메뉴는 유지한다. 만기에도 자동 해지되지 않는다.
- 약관·모의 금리·세금은 시연 정책임을 화면에 표시한다. 실제 예금자보호/우대금리/은행 약관 문구를 추가하지 않는다.

## 최종 협의 항목

| 항목 | 백엔드 현재 상태 | 프론트/통합 때 결정할 내용 |
|---|---|---|
| API 주소·CORS | 기존 설정 유지 | 개발/운영 origin, 프록시/TLS, 배포 URL |
| 구 API | 호환 유지 | 새 화면 전환 일정과 차단 시점 |
| 모의 연락처 | 기본 OFF, demo-verification에서만 수신함 | 개발 전용 중계/UI, 공유 키를 프론트 번들에 넣지 않기 |
| 복구 코드 | 5개, 원문은 발급 시 한 번 | 보관 안내/확인 화면, 응답 유실 시 재발급 |
| 예적금 | 본 문서의 모의 고정 조건 | 조건 표기/해지 확인 화면/수동 납입 버튼 |
| 테스트 데이터 | H2는 재시작 시 소멸 | 시연 계정·초기 잔액·재생성 절차 |
| 실제 DB | V11까지 추가, 실제 PostgreSQL 미검증 | 백업·이전·동시성·키 주입·복구 리허설 |
| 다중 서버 | 일부 제한기는 단일 프로세스 메모리 | 공유 rate limiter·프록시 IP 정책 |

## 실행/검증 전달

Java 17, Maven 3.9+. `mvn test`, `mvn package`. 서버 실행은 서로 다른 32바이트 Base64 BANK_ENCRYPTION_KEY/BANK_LOOKUP_KEY를 준비한다. 공개 테스트 키는 운영/실데이터에 사용하지 않는다. 상세 키·실행 절차는 IMPLEMENTATION_STAGE1.md, PostgreSQL 계획은 WINDOWS11_POSTGRES.md를 참조한다. 실제 DB 이전은 아직 수행하지 않았다. 이번 검증 범위와 결과는 VALIDATION_STAGE6.md다.
