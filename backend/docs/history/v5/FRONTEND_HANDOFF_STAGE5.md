# 프론트 연동 안내 — 5차 중간 계약

이번 산출물은 백엔드 API와 계약이다. 실제 프론트 화면·문자/메일 서비스는 포함하지 않는다. 기존 2~4차 계약은 유지하며 신원 관련 흐름은 STAGE5_API.md를 우선한다.

| 화면 | 호출 순서 |
|---|---|
| 가입 | GET terms → 필수 약관 선택 → 선택적으로 REGISTER challenge/verify → POST auth/register + Idempotency-Key |
| 모의 연락처 인증 | contact-challenges → 개발 전용 demo/inbox → contact-challenges/{id}/verify |
| 추가 연락처 | 로그인 → PROFILE challenge/verify → PUT me/contact + 현재 비밀번호 |
| 복구 코드 보관 | 로그인 → 현재 비밀번호 재확인 → POST me/recovery-codes →5개를 한 번 표시 |
| 코드 보관 상태 | GET me/recovery-codes →남은 개수만 표시 |
| 아이디 찾기 | POST recovery/username + 복구 코드 →실제 아이디 표시, 코드1개 소비 |
| 비밀번호 분실 | POST recovery/password + 아이디/복구 코드/새 비밀번호 →로그인 화면 |
| 비밀번호 변경 | PUT me/password + 현재/새 비밀번호 →로그인 화면 |
| 계좌 PIN 분실 | 로그인 → POST accounts/{id}/pin/reset + 현재 로그인 비밀번호/복구 코드/새 PIN →재로그인 |

## 화면 동작

- 회원가입 완료 응답은 customerId만 있다. 로그인 후 복구 코드 발급·보관 안내까지 별도 단계로 연결한다.
- 연락처는 선택이다. 기본 실행은 발송이 비활성화돼 있으므로 연락처 생략 가입을 허용한다. 연락처를 인증했다고 표시하려면 모의 절차 결과를 구분해야 한다.
- emailAssurance/phoneAssurance=SIMULATED는 ‘모의 인증 완료’, UNVERIFIED는 ‘미인증’. emailVerified/phoneVerified=false를 실제 인증으로 덮어쓰지 않는다.
- 약관 text는 시연 초안임을 표시한다. 실제 서비스 동의문으로 사용하지 않는다. 기존 사용자 GET me/terms의 빈 목록은 과거 동의 기록이 없다는 뜻이다.
- 계좌복구 화면에서 이메일·전화번호 인증만으로 비밀번호를 바꾸는 흐름을 만들지 않는다. 모의 수신함과 복구 코드는 별개다.
- 인증번호/복구 코드/PIN/password는 문자열로 취급하고 URL·로그·분석 이벤트·영구 브라우저 저장소에 넣지 않는다.
- demo/inbox는 개발 프로필에서만 있다. 공유 개발 키는 일반 프론트 소스에 넣지 않는다. 실제 수신함 UI가 필요하면 개발 전용 서버 중계에서 보관한다.
- 재발송60초, 코드유효5분, 5회오입력시새요청필요. 인증 성공 contactGrant도5분이며 한 번만 사용할 수 있다. 필드/사용자/용도가 달라지면 새 요청으로 진행한다.
- 복구 코드는5개를 발급 때만 보여준다. ‘다시 보기’는 없고 재발급하면 이전5개는 폐기된다. 화면 이탈 전 별도 보관 안내를 한다.
- 아이디 찾기는 코드1개를 소비한다. 이어 비밀번호 복구를 한다면 남은 다른 코드를 사용한다.
- 비밀번호 변경/복구/PIN 재설정 성공204 후 로그인·승인 토큰과 복구 코드 상태를 모두 지운다. 재로그인 후 새 코드 발급을 안내한다.
- PIN 재설정은 일반 PIN 변경과 다르다. 현재 PIN 대신 로그인 비밀번호+복구 코드를 요구한다.
- REAUTHENTICATION_FAILED 401은 입력 비밀번호 오류이고 UNAUTHORIZED 401은 재로그인 필요다. 모든401을 동일 처리하지 않는다.
- 가입 응답 유실은 같은 Idempotency-Key/본문으로 재시도한다. 복구 코드 발급 응답 유실은 로그인 상태에서 재발급한다.
- 비밀번호 재설정 응답이 불명확하면 우선 새 비밀번호 로그인을 시도한다. 이미 성공한 복구 코드는 재사용할 수 없다.
- 복구 코드까지 잃은 사용자에 대한 자동/관리자 우회 복구 화면은 이번 범위에 없다.

## 기존 경로와 협의할 내용

구 `/api/auth/register`는 기본 가입 호환용이며 신규 약관/연락처 정책을 강제하지 않는다. 새 가입 화면은 `/api/v2/auth/register`로 전환하고 구 API 폐기는 전체 프론트 전환 일정과 함께 협의한다. 로그인은 구·신 주소 모두 인증 버전/재설정 순서 제어를 적용한다.

이번 변경으로 me 응답에 assurance 필드가 추가된다. 프로필 PUT에서 연락처를 바꾸면 모의 인증 상태가 초기화된다. 프로필 version을 다시 받아 저장한다.

최종 통합 때 프록시 뒤의 IP 제한, 개발 전용 수신함 접근 경로, 복구 코드 보관 화면, 기본/개발 실행 모드를 협의한다. 실제 DB 인프라 통합과 전체 프론트 최종 명세는 예정대로 마지막에 진행한다.
