# 백엔드 v6.1 — 합의한 5개 수정

2026-10-03. 기준: `bank-backendv6.zip`의 v6 소스. 배포본 버전은 v6.1이며 API 경로는 기존 `/api/v2`를 유지합니다.

## 변경 및 프론트 영향

| 수정 | 백엔드 반영 결과 | 프론트에서 적용할 내용 |
|---|---|---|
| 1. 멱등키 오류 통일 | 누락·형식 오류는 HTTP 400 / `IDEMPOTENCY_KEY_INVALID`. 같은 키로 다른 요청은 기존대로 HTTP 409 / `IDEMPOTENCY_KEY_CONFLICT` | 예적금의 이전 `INVALID_IDEMPOTENCY_KEY` 분기를 새 코드로 변경. 가입도 동일한 코드로 처리. 전환 중에는 구 코드도 함께 처리할 수 있음 |
| 2. 새 비밀번호 오류 위치 | 변경·복구 API에서 길이, UTF-8 72바이트 초과, 정책 위반, 기존 비밀번호 재사용 오류의 `field`는 `newPassword` | `newPassword` 입력란에 오류 표시. 가입 비밀번호 오류는 `password` 유지 |
| 3. 재인증 제한 분리 | 비밀번호 실패 제한과 전체 요청 제한을 아래 정책으로 분리 | 429의 `Retry-After` 초만큼 재인증 제출을 막고 남은 시간 안내. 제한 중 자동 재시도 금지. 401은 비밀번호 오류 표시 |
| 4. 가입 감사 로그 | 가입 요청당 JSON 이벤트 1개. 성공은 커밋 후, 재전송은 별도 `REPLAY`, 실패는 오류 코드 기록 | 가입 화면/API 변경 불필요. 로그는 서버 담당자가 확인하며 브라우저에 로그 조회 기능을 추가하지 않음 |
| 5. 가입 성공 재전송 순서 | 이미 성공한 같은 요청은 신규 가입 IP 한도 검사 전에 기존 결과 반환. 동시 요청도 사용자 1명만 생성 | 응답 유실 후 동일한 키·동일한 본문을 유지해 재전송. 성공 여부가 불명확할 때 새 키·새 인증 권한으로 바꾸지 않음 |

키 검사는 정상 인증·본문 검증을 통과한 요청에 적용합니다. 본문 자체가 잘못됐거나 세션이 만료된 요청은 기존 입력/인증 오류가 먼저 반환될 수 있습니다. 키는 소문자 표준 UUID입니다.

## 1. 멱등키 적용 API

| HTTP | 경로 |
|---|---|
| POST | `/api/v2/auth/register` |
| POST | `/api/v2/accounts` |
| POST | `/api/v2/demo/deposits` (`demo` 프로필) |
| POST | `/api/v2/transfers` |
| POST | `/api/v2/savings` |
| POST | `/api/v2/savings/{id}/payments` |
| POST | `/api/v2/savings/{id}/closure` |

```json
{"code":"IDEMPOTENCY_KEY_INVALID","message":"Idempotency-Key는 소문자 표준 UUID여야 합니다."}
```

분기에는 `code`를 사용합니다. 안내 `message`의 문구를 비교하지 않습니다.

## 2. 새 비밀번호

- `PUT /api/v2/me/password`
- `POST /api/v2/recovery/password`

검증 오류 `INVALID_INPUT`과 정책 오류 `WEAK_CREDENTIAL` 모두 새 비밀번호 문제라면 `field: "newPassword"`입니다. 현재 비밀번호 오류, 만료된 복구 권한 등의 다른 오류는 기존 계약을 유지합니다.

## 3. 재인증 제한의 정확한 동작

대상은 `POST /api/v2/auth/step-up`의 이체 승인과 계좌 설정 승인입니다. 같은 사용자라면 목적을 바꿔도 두 제한을 공유합니다.

| 조건 | 처리 |
|---|---|
| 최근 5분 내 비밀번호 오류 1~4회 | 401 `REAUTHENTICATION_FAILED` |
| 최근 5분 내 5번째 비밀번호 오류 | 그 시점부터 5분 차단. 429 `RATE_LIMITED`, `Retry-After: 300` |
| 올바른 비밀번호 | 실패 횟수를 추가하지도 초기화하지도 않음 |
| 최근 1분 내 전체 승인 요청 30회 | 30회까지 허용, 31번째부터 429. 성공·실패·서비스 검증 실패도 요청 한도에 포함 |
| 차단 중 요청 | 비밀번호 비교를 실행하지 않음. 차단 종료 시각도 연장하지 않음 |
| 두 제한이 동시에 적용 | 더 긴 남은 대기 시간을 `Retry-After`로 반환 |
| 기간 경계 | 최근 1분·5분의 이동 구간을 기준으로 오래된 기록 제거 |

HTTP 헤더의 `Retry-After`는 양의 정수 초이며 올림 계산합니다. 이 헤더를 모든 API의 429가 제공한다는 의미는 아닙니다. 프론트가 BFF/프록시를 사용한다면 이 헤더를 전달해야 합니다. 별도 출처에서 브라우저가 직접 호출하도록 구성한다면 허용된 출처에 이 헤더가 노출되는지도 연동 검수해야 합니다.

로그인 비밀번호 3회 잠금, 계좌 PIN 4회 잠금, 프로필·예적금·복구의 기존 제한은 바꾸지 않았습니다. 비밀번호 실패 횟수는 DB 트랜잭션 롤백과 무관하게 유지합니다.

**실행 범위:** 이 제한기는 단일 JVM 메모리 기준입니다. 서버 재시작 시 초기화되고 여러 서버 인스턴스끼리는 공유하지 않습니다. 다중 인스턴스 배포 시에는 공유 저장소 기반 제한기가 필요합니다. 이번 변경에 DB 통합이나 외부 저장소 도입은 포함하지 않았습니다.

## 4. 가입 로그

로거 이름은 `BANK_REGISTRATION_AUDIT`이며 서버 표준 출력에 다음 필드의 JSON 한 줄을 출력합니다. 기존 일반 서버 로그와 함께 출력되므로 수집기는 `event=registration`인 JSON 행을 구분합니다. Splunk 송신기나 외부 수집 서비스는 추가하지 않았습니다.

| 필드 | 값 |
|---|---|
| `event` | `registration` |
| `timestamp` | UTC ISO 8601 |
| `outcome` | `SUCCESS`, `FAILURE`, `REPLAY` |
| `reasonCode` | 실패 API 코드. 성공·재전송은 null |
| `customerId` | 커밋된 성공/재전송의 고객 공개 ID. 확정되지 않으면 null |
| `phoneCorrelationId` | 정규화된 번호의 HMAC-SHA-256. 키는 `BANK_LOOKUP_KEY`, 전용 도메인 `audit.registration.phone`. 안전하게 확인할 수 없으면 null |
| `sourceIp` | 서버가 직접 연결에서 확인한 상대 주소. 클라이언트의 `X-Forwarded-For`를 읽지 않음 |

성공 이벤트는 트랜잭션 커밋 후에만 기록합니다. 롤백한 가입을 성공으로 집계하지 않습니다. HTTP 응답 전달 전에 연결이 끊겨도 DB 커밋이 끝났다면 가입 자체는 성공이며, 재전송으로 결과를 다시 확인합니다. 로그는 DB와 원자적으로 저장되는 별도 감사 테이블/아웃박스가 아니므로 프로세스 강제 종료나 로그 저장 장애까지 전달을 보장하지 않습니다.

휴대폰 원문, 이름, 비밀번호, PIN, 인증번호, 연락처 확인 권한, 로그인 토큰, 복구 코드, 요청 본문은 이벤트에 기록하지 않습니다. 프록시 뒤에서는 `sourceIp`가 프록시 주소일 수 있습니다. 신뢰할 프록시 설정 없이 전달 헤더를 사용하지 않습니다.

## 5. 가입 재전송 순서와 호환

1. 키 형식을 검사하고 요청 해시를 계산합니다.
2. 성공 이력이 있으면 본문이 같을 때 기존 `customerId`와 HTTP 201을 반환합니다.
3. 같은 키의 다른 본문은 409 `IDEMPOTENCY_KEY_CONFLICT`입니다.
4. 성공 이력이 없는 신규 요청에만 기존 IP별 1시간 20회 제한과 신규 가입 검증을 적용합니다.
5. 회원·약관 동의·성공 이력을 같은 트랜잭션으로 저장합니다.

재전송은 이미 사용된 연락처 확인 권한을 다시 소비하지 않으며 신규 가입 제한도 소비하지 않습니다. 신규 요청의 기존 트랜잭션 롤백 규칙은 유지합니다. 단순히 모든 HTTP 시도를 영속적으로 세는 새 IP 방어 정책을 도입한 것은 아닙니다.

새 해시는 제출된 약관 맵까지 반영합니다. v6 방식으로 저장한 성공 이력도 기존 필수 약관과 본문이 일치할 때 재전송할 수 있습니다. 기존 DB 스키마와 암호화/조회 키를 유지하며 추가 마이그레이션은 필요하지 않습니다.

## 검증 자료

실행 결과는 `VALIDATION_V6_1.md`를 확인합니다. 기존 v6 문서는 이전 기반 계약이며 위 변경 항목은 본 문서를 우선 적용합니다. 프론트 코드와 실제 브라우저/BFF 연동은 이번 자동 테스트의 대상이 아닙니다.
